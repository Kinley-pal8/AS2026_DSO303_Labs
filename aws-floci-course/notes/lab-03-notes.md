## Step 11: a policy that names a bucket that does not exist yet

An IAM policy is a statement about ARNs, not a reference to objects, so `USMSStudentDataReadWrite` is valid today even though `arn:aws:s3:::usms-student-data` does not exist yet; it simply has no effect until something appears at that ARN.

## Review Questions

### 1. The five inputs to Step 8, and how each would fail

**Subnet (Lab 2).** A missing or empty subnet ID fails immediately with `InvalidSubnetID.NotFound`. A *wrong but valid* subnet is the dangerous case and fails silently: if `$USMS_PRIVATE_SUBNET_A` had been substituted, the web server would launch happily with no public address and no internet route, and the only symptom would be that nobody can reach the portal. **Security group (Lab 2).** An empty or deleted group ID fails immediately with `InvalidGroup.NotFound`. A wrong group (for example `usms-db-sg` or the VPC `default` group) launches without complaint and silently blocks port 80, again surfacing only as an unreachable site. **Instance profile (Lab 1).** A missing profile fails immediately with `InvalidParameterValue: iamInstanceProfile.name`. A profile that exists but holds no role, or holds a role without `USMSStudentDataReadWrite`, is silent until Lab 4, when the first S3 call returns `AccessDenied` or `Unable to locate credentials` from inside the instance. **Key pair (Lab 3).** A missing key fails immediately with `InvalidKeyPair.NotFound`. The wrong key (one whose private half you do not hold) is silent until you need SSH, which is precisely during an incident. **User-data script (Lab 3).** This is the most silent of all: EC2 accepts any bytes under 16 KB, so a syntax error, an unquoted heredoc that expanded `${INSTANCE_ID}` on the laptop, or (as observed here) `dnf` on an Amazon Linux 2 image all produce a `running` instance that serves nothing. The only evidence is `/var/log/usms-bootstrap.log` or `/var/log/cloud-init-output.log` on the instance. In short, the API validates *existence* immediately but cannot validate *intent*; every wrong-but-valid input fails silently.

### 2. A policy for a bucket that does not exist

`USMSStudentDataReadWrite` is valid because IAM policies are evaluated against the ARN in a request, not against a catalogue of existing resources; IAM never checks that `arn:aws:s3:::usms-student-data` exists, only that the string is a well-formed ARN. This decoupling is deliberate: it lets permissions be written before resources are created (as infrastructure-as-code does), and it means a policy survives a bucket being deleted and re-created with the same name. For `usms-web-01` today, the policy grants nothing usable: any S3 call to that bucket would be authorised by IAM and then fail at S3 with `NoSuchBucket` (404), which is exactly what Exercise 5's `head-bucket` captured, while calls to any other bucket are implicitly denied. The moment Lab 4 runs `create-bucket usms-student-data`, nothing in IAM changes at all, but the ARN now resolves to a real resource, so the same instance credentials immediately gain `ListBucket` and `GetBucketLocation` on the bucket and `GetObject`, `PutObject` and `DeleteObject` on its objects, while the explicit `Deny` on `s3:DeleteBucket` begins protecting it. The `head-bucket` that returned 404 in Exercise 5 will return 200 with no change to the role, the profile or the instance.

### 3. "Restarting the instance redeploys it"

It does not work because cloud-init runs user-data scripts once per instance, keyed on the instance ID it records under `/var/lib/cloud/instances/`. A stop/start or reboot keeps the same instance ID, so cloud-init sees the instance as already provisioned and skips the script. (Floci, which re-ran nothing on start, behaves the same way here.) Worse, the colleague's mental model would leave production running whatever version was current at first boot while everyone believes a restart refreshed it. Two approaches that do work: **(a) immutable deployment.** Bake each release into a new golden AMI (as Step 20 began) or put a short bootstrap in a launch template, then replace instances: an Auto Scaling group instance refresh or a blue/green swap behind a load balancer (Lab 8). Deployment becomes "launch new, drain old", and rollback is "point at the previous AMI". **(b) An explicit deployment agent.** Use a tool that runs on demand against running instances: AWS Systems Manager Run Command or State Manager, CodeDeploy, or a configuration-management tool. The deployment step is versioned and auditable, and is triggered by the pipeline rather than by a reboot. (A per-boot cloud-init module or a systemd unit that pulls the latest release on start would also work technically, but it couples deployments to reboots, which is the same confusion in a more reliable form.)

### 4. Auto-assigned public address versus Elastic IP

**Ownership.** An auto-assigned address belongs to AWS's pool and is lent to the instance's primary network interface. An Elastic IP is allocated to *your account* and stays yours until you release it. **When it changes.** The auto-assigned address is released on every stop (and on terminate) and a different one is issued on start. An Elastic IP never changes; it only moves when you re-associate it. **Cost.** Since 2024 AWS charges for every public IPv4 address (about USD 0.005 per hour, roughly USD 3.65 per month), auto-assigned or elastic; the historic difference was that an Elastic IP *not* associated with a running instance was billed while an associated one was free, and the surprise bill for idle Elastic IPs still applies. **On stop.** The auto-assigned address disappears (`PublicIpAddress: None` while stopped) and comes back as a different address. The Elastic IP stays associated and returns unchanged when the instance starts. On Floci the stop transition never completed and the address field never cleared, so this was reasoned rather than observed. **A failover only the Elastic IP makes possible.** DNS for `portal.usms.edu` points at `54.77.99.130`. When `usms-web-01` fails, an operator (or a script triggered by a CloudWatch alarm) runs `aws ec2 associate-address --allocation-id eipalloc-44a8… --instance-id <usms-web-02> --allow-reassociation`, and within seconds the same address answers from the standby instance in the other AZ, with no DNS change, no TTL wait and no client reconfiguration. With auto-assigned addresses the standby has a different IP, so failover requires a DNS update and waiting out every resolver's cache.

### 5. Volumes are zonal, snapshots are regional

An EBS volume is a block device replicated *within* one Availability Zone, on storage hardware physically near the instances it serves (that proximity is what gives it single-digit-millisecond latency). It cannot attach across AZs because it exists only in one AZ's data centres; Floci enforced this too, rejecting the attach from `us-east-1b`. A snapshot is stored in Amazon S3, which is a regional service replicated across multiple AZs, so it can be restored as a new volume in any AZ of the region. The implication for a system that must survive the loss of one AZ: the data on a single EBS volume shares the fate of its AZ, so you need either (a) frequent snapshots (AWS Backup or Data Lifecycle Manager) so the volume can be rebuilt in a surviving AZ, accepting the recovery-point gap since the last snapshot and the restore time, or (b) continuous replication to a second AZ at the application or database layer, which is exactly what RDS Multi-AZ does and why Lab 6 replaces `usms-db-01` with a managed RDS instance. Copying snapshots to another region extends the same reasoning to the loss of a region.

### 6. Is checking six configuration properties an adequate substitute?

It is an adequate substitute for proving that *the AWS network configuration under my control* is correct, and it is how real "I cannot reach my instance" incidents are diagnosed: each of the six checks corresponds to one hop a packet must pass (internet gateway attachment, route table, network ACL, security group, a public address, a running instance), and a fault in any one of them is sufficient to break reachability. It is *not* an adequate substitute for proving the application works, for three reasons. It verifies configuration, not behaviour: it trusts that AWS enforces what the API reports. It is incomplete even as configuration: check 6 only reports that the default NACL is attached, not that its rules allow the traffic. And it cannot see anything inside the instance. The class of fault it cannot detect is **host- and application-level faults**: the process not running or not listening on port 80, the bootstrap failing, an OS firewall, the service bound to `127.0.0.1`, or a crash after start. This lab produced exactly that fault: all six checks passed while `/var/log/usms-bootstrap.log` shows `dnf: command not found`, so nginx was never installed. The configuration checks therefore prove necessary conditions; only an end-to-end request (or a load balancer health check) proves sufficiency.

### 7. Every difference between `usms-web-01` and `usms-db-01`

| Difference | `usms-web-01` | `usms-db-01` | Property of |
|---|---|---|---|
| Subnet | `usms-public-subnet-a` | `usms-private-subnet-a` | Instance (chosen at launch) |
| Private address range | `10.0.1.0/24` | `10.0.3.0/24` | Subnet |
| Public IPv4 address | auto-assigned at launch | none | Subnet (`MapPublicIpOnLaunch` True vs False) |
| Elastic IP | `usms-web-eip` associated | none | Instance (association) |
| Route to the internet | `0.0.0.0/0 -> usms-igw` (inbound and outbound) | `0.0.0.0/0 -> usms-nat` (outbound only) | Subnet (its route table) |
| Route to S3 | via the internet gateway | via `usms-s3-endpoint` (gateway endpoint on the private route table) | Subnet (its route table) |
| Network ACL | VPC default (allow all) | `usms-private-nacl` | Subnet |
| Security group | `usms-app-sg` (80, 443 from anywhere; 22 from the VPC) | `usms-db-sg` (5432 from `usms-app-sg` only) | Instance (its network interface) |
| IAM instance profile | `usms-ec2-app-profile` | none (least privilege) | Instance |
| User data | nginx bootstrap | none | Instance |
| Data volume | `usms-web-data-vol` on `/dev/sdf` | root volume only | Instance (attachment) |
| Tags | `Name=usms-web-01`, `Tier=web` | `Name=usms-db-01`, `Tier=data` | Instance |
| Availability Zone | `us-east-1a` | `us-east-1a` (same) | Subnet |

Things that are the same, by design: instance type `t3.micro`, AMI, key pair `usms-app-key`, VPC, Availability Zone, and the VPC-wide properties (CIDR `10.0.0.0/16`, DNS support and hostnames, the `local` route that lets them talk to each other). No difference between them is a property of the VPC, since both sit in the same VPC; every difference is either chosen per instance at launch or inherited from the subnet the instance was placed in, which is the point of Lab 2: "public" and "private" are properties of subnets and their route tables, not of instances.
