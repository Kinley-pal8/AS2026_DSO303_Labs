## Review Questions

### 1. "I put auto scaling on the task definition"

That is wrong at every level. A task definition is an immutable, versioned blueprint (`usms-enrolment:1`, `:2`). It contains no count, so there is nothing on it to scale, and you cannot attach anything to a revision because you can never change one. In Lab 06, auto scaling is attached to the **service**, registered with Application Auto Scaling as a **scalable target** whose resource ID is `service/usms-ecs-cluster/usms-enrolment-svc` (the suffix of the service ARN Step 10 produced), with the dimension `ecs:service:DesiredCount`. The only thing a scaling policy ever modifies is the service's **`desiredCount`**. It does not start or stop a single task itself. The **service** (its scheduler and reconciliation loop) is what makes reality match, by starting or stopping tasks until `runningCount` equals `desiredCount`, exactly as Step 11's "Your turn" showed by hand (2 → 3 → 2, with the container count following). ECS itself knows nothing about the scalable target, and the observable consequence is that the two can fight. If someone runs `update-service --desired-count 5` by hand, ECS obeys immediately, but the next scaling evaluation can move it straight back inside the target's min/max. Conversely, `describe-services` never shows the min, max or policy, so you must look in `application-autoscaling describe-scalable-targets` / `describe-scaling-activities` to learn why the count changed. Similarly, deleting the service does not delete the scalable target, which is why `lab-06-cleanup.sh` has to run first.

### 2. One policy, two delivery mechanisms

At runtime, Lab 03's EC2 instance obtains credentials through the **instance profile**: EC2 assumes `usms-ec2-app-role` on the instance's behalf and serves short-lived, automatically rotated credentials from the Instance Metadata Service at `169.254.169.254`, where the SDK's default credential chain finds them. This lab's Fargate task obtains credentials through the **task role**: the ECS agent assumes `usms-ecs-task-role` (which trusts `ecs-tasks.amazonaws.com`) for that specific task and serves credentials from a task-scoped endpoint named in the container's `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` variable, which the same default chain checks before IMDS. Neither needs a key on disk because in both cases the credential is minted by STS for a role, delivered over a local endpoint only the workload can reach, and expires within hours. There is nothing long-lived to steal, rotate or accidentally commit, and the code (Lab 03's `transcript-upload.sh`) contains no credentials at all. And because `USMSStudentDataReadWrite` grants access to the ARN `arn:aws:s3:::usms-student-data`, not to an object that exists, **both** chains change at the same instant when the bucket is created: nothing in IAM, the instance profile, the task definition or the service is touched, yet the instance and every enrolment task immediately gain `ListBucket` on the bucket and `GetObject`/`PutObject`/`DeleteObject` on its objects. The explicit `Deny` on `s3:DeleteBucket` also begins protecting it, and the 404 from Lab 03 Exercise 5's `head-bucket` becomes a 200 for both.

### 3. Telling the two roles apart

**Execution role wrong:** the task never reaches `RUNNING`, and `stoppedReason` names the image pull (`CannotPullContainerError`), the registry or the log driver, so *your code never ran*. **Task role wrong:** the task starts and stays `RUNNING`, then the application logs `AccessDenied` (or "Unable to locate credentials") when it calls S3, so *your code ran and was refused*. They share an identical trust policy because trust answers a different question from permissions. Trust says *who may assume the role*, and both roles are assumed by the same principal, the ECS tasks service (`ecs-tasks.amazonaws.com`): once on behalf of the platform before the container starts, once on behalf of the container while it runs. What separates them is the **permissions policy** attached to each (`USMSECSTaskExecution` versus `USMSStudentDataReadWrite`) and **which field of the task definition names them** (`executionRoleArn` versus `taskRoleArn`). The verify script's "exec role and task role are DIFFERENT" check exists because pointing both fields at one role silently gives the platform the application's data permissions, or the application the platform's.

### 4. A group reference, not a CIDR

Even with a fixed count of two, `10.0.1.0/24` would be the wrong rule. A CIDR grants access to *every* address in the public subnet: the NAT gateway's interface, any future instance anyone launches there, and anything that happens to land in that range, none of which should call the enrolment API. Meanwhile it would *miss* a legitimate web server in `usms-public-subnet-b` (`10.0.2.0/24`), such as Lab 03's `usms-web-02`. A group reference states the actual intent ("whatever is a web-tier member, wherever it runs"). It follows membership rather than addresses, and survives re-IPs, relaunches and new subnets. The additional reason it becomes close to mandatory in Lab 06 is churn: once the count moves, tasks and web instances are created and destroyed continuously, each with a new, unpredictable private IP from anywhere in a /24. No CIDR list can be kept current, while a group reference needs no change at all. The same reasoning applies in the other direction, and is why Lab 05 can switch the only caller to the load balancer's group by editing one rule.

### 5. What Fargate removes, and what it does not

Fargate removes everything Lab 03 had to own *below* the application. There is no AMI to choose or patch, no instance type, no key pair or SSH, no user-data bootstrap, no EBS root volume, no instance profile, and no capacity to provision. You declare CPU and memory per task (`256`/`512`) and AWS finds the hardware. What it does **not** remove is the network. With `awsvpc`, each task gets its own elastic network interface **in my subnet** (`usms-private-subnet-a`/`-b`), with a private address from that subnet, **my security group** (`usms-enrolment-sg`) on that interface, and **my route tables** deciding where its packets go. That is why the private tasks reach `public.ecr.aws` only through Lab 02's `usms-private-rt` → `usms-nat` → `usms-igw` (and S3 layers via `usms-s3-endpoint`), and why deleting the NAT gateway would make every task fail with an image-pull timeout. Identity also remains my job: I still write the execution role and the task role. Fargate is "serverless" for compute, not for networking or IAM.

### 6. A command that cannot tell `memory` from `hybrid`, and one that can

`aws sts get-caller-identity` (or `./scripts/utilities/whoami.sh`) looks identical in both modes before and after a restart: the account `000000000000` and the root identity are constants Floci fabricates on every boot, so an unchanged answer is not evidence that anything persisted. `aws ecs describe-services --cluster usms-ecs-cluster --services usms-enrolment-svc` would not look identical. In `hybrid` mode, state is flushed to `~/floci-data`, so after a restart the cluster and service are still there (`ACTIVE`, `desiredCount` 2, the same subnets and security group). In `memory` mode Floci starts empty, and the same call fails with `ClusterNotFoundException`. The difference is that the identity is *computed*, whereas the service is *stored*: only a read of something this lab created can prove persistence. Lab 03 showed the subtler version of this: after a restart, the stored *records* survive but the *running* state can change (instances came back `stopped`), so a good persistence check compares the configuration (IDs, subnets, groups, counts), not only that something answered.
